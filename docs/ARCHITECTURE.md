# 앱 구조 및 데이터 계약

## 1. 설계 목표

- 화면 코드와 데이터 요청 코드를 분리한다.
- 한 기능에 관련된 화면, 상태, 위젯을 같은 폴더에 두어 실행 흐름을 쉽게 따라간다.
- 관심 종목은 앱을 종료한 뒤에도 유지한다.
- 주가처럼 변경되는 데이터는 저장하지 않고 Naver API에서 다시 조회한다.
- 과제 규모에 맞게 필요한 구조만 사용한다.

## 2. 폴더 구조

```text
lib/
├── main.dart                         앱 실행 시작점
├── app/
│   ├── app.dart                      앱 테마와 첫 화면 구성
│   └── app_controller.dart           하단 탭과 앱 공통 상태 관리
├── data/
│   ├── dtos/                         Naver 응답 필드 파싱과 모델 변환
│   ├── models/                       주식, 시세, 상세, 일봉 모델
│   ├── naver_stock_service.dart      Naver API 요청과 응답 변환
│   └── favorite_storage.dart         관심 종목 코드 로컬 저장
├── features/
│   ├── favorites/
│   │   └── favorite_controller.dart  화면들이 공유하는 관심 종목 상태
│   ├── watchlist/
│   │   ├── watchlist_screen.dart
│   │   ├── watchlist_controller.dart
│   │   └── widgets/
│   ├── search/
│   │   ├── search_screen.dart
│   │   ├── search_controller.dart
│   │   └── widgets/
│   └── stock_detail/
│       ├── stock_detail_screen.dart
│       ├── stock_detail_controller.dart
│       └── widgets/
├── shared/
│   └── widgets/                      여러 기능에서 함께 쓰는 위젯
└── theme/                            회사에서 제공한 디자인 토큰과 테마
```

회사가 제공한 `theme`과 Flutter 플랫폼 폴더는 유지하고, 나머지 앱 구조는 요구사항에 맞게 직접 구성한다.

현재 요구사항에는 관계형 데이터 조회나 대량 데이터 저장이 없으므로 별도의 DB 계층은 두지 않는다. `shared_preferences`는 DB가 아니라 간단한 값을 저장하는 로컬 키-값 저장소로 사용한다.

## 3. 데이터 저장 기준

### 메모리 상태

앱이 실행되는 동안 필요한 값은 각 기능의 controller에서 관리한다.

- 현재 선택된 탭
- 관심 종목 목록
- 선택된 정렬 방식
- API 응답 데이터
- 로딩 및 오류 상태
- 일봉 데이터 캐시

### 기기 저장소

관심 종목의 종목 코드는 `shared_preferences`의 `SharedPreferencesAsync` API를 사용해 문자열 목록으로 저장한다.

```text
["005930", "000660", "035720"]
```

종목명, 현재가, 등락률은 저장하지 않는다. 앱을 다시 실행하면 저장된 종목 코드를 읽고 Naver API에서 최신 정보를 조회한다.

## 4. Naver API 계약

Naver의 응답을 화면에서 직접 사용하지 않는다. `data/dtos`에서 외부 응답을 읽고 앱 모델로 변환한 뒤 각 기능의 controller에 전달한다.

### 종목 검색

```text
searchStocks(query) -> List<Stock>
```

- 입력: 사용자가 입력한 종목명 또는 종목 코드
- 출력: 국내 주식 검색 결과
- 국내 종목이며 종목 코드가 6자리인 항목만 사용한다.
- 앱 내부 식별자는 `domestic:{종목 코드}` 형식으로 통일한다.
- 사용자가 입력을 멈춘 뒤 검색을 요청해 불필요한 연속 호출을 줄인다.
- 이전 요청보다 나중에 시작한 요청의 결과만 화면에 반영한다.
- 검색어가 비어 있으면 API를 호출하지 않고 검색 전 안내 상태를 표시한다.

### 실시간 시세 조회

```text
fetchQuotes(symbols) -> Map<String, StockQuote>
```

- 입력: 종목 코드 목록
- 출력: 종목 코드별 현재가, 전일 종가, 등락 금액, 등락률, 거래량
- 여러 종목은 한 번의 요청으로 조회한다.
- 응답에 없는 종목은 전체 요청 실패로 처리하지 않고 해당 종목만 조회 불가 상태로 표시한다.

### 종목 상세 조회

```text
fetchStockDetail(symbol) -> StockDetail
```

- 입력: 종목 코드 한 개
- 출력: 종목명, 시장, 현재가, 전일 대비, 등락률, 시가, 고가, 저가, 거래량, 상장 주식 수
- 시가총액은 API에서 제공되는 값을 우선 사용하고, 필요한 경우 현재가와 상장 주식 수로 계산한다.

### 일봉 조회

```text
fetchDailyPrices(symbol, period) -> List<DailyPrice>
```

- 입력: 종목 코드와 조회 기간
- 출력: 날짜, 시가, 고가, 저가, 종가, 전일 대비, 거래량으로 구성된 일봉 데이터
- 지원 기간: 1개월, 3개월, 6개월, 1년
- 기간별 조회 페이지 수는 1개월 2페이지, 3개월 6페이지, 6개월 12페이지, 1년 25페이지를 기준으로 한다.
- Naver Finance HTML의 문자 인코딩을 변환한 뒤 필요한 값만 모델로 만든다.
- 화면의 일별 시세는 최신 날짜가 위에 오도록 정렬한다.
- 차트는 날짜가 과거에서 최신 순서가 되도록 정렬한다.

## 5. 로컬 저장 계약

```text
loadFavoriteSymbols() -> List<String>
saveFavoriteSymbols(symbols) -> void
```

- 저장 대상은 관심 종목 코드 목록뿐이다.
- 중복된 종목 코드는 저장하지 않는다.
- 관심 종목을 추가하거나 삭제할 때마다 전체 목록을 다시 저장한다.
- 저장된 값이 없거나 읽기에 실패하면 빈 목록으로 시작한다.

## 6. 캐시 기준

- 검색 결과와 현재가는 최신성이 중요하므로 화면 진입 또는 새로고침 시 다시 조회한다.
- 일봉 데이터는 `종목 코드 + 조회 기간`을 키로 메모리에 보관한다.
- 같은 종목과 기간을 다시 선택하면 캐시를 먼저 사용한다.
- 앱을 종료하면 일봉 캐시는 삭제된다.

## 7. 로딩 및 오류 처리

- 관심 종목 시세를 불러오는 동안 종목별 가격 영역에 스켈레톤을 표시한다.
- 검색 중에는 이전 검색 결과를 임의로 새로운 검색어의 결과처럼 표시하지 않는다.
- 검색 결과가 비어 있으면 검색 결과 없음 상태를 표시한다.
- 상세 정보와 일봉은 각각 로딩 상태와 오류 상태를 가진다.
- 일부 데이터만 실패하면 정상적으로 받은 데이터는 유지하고 실패한 영역만 다시 시도할 수 있게 한다.
- 네트워크 요청 실패 메시지는 서비스의 원문을 그대로 노출하지 않고 사용자가 이해할 수 있는 문장으로 변환한다.

## 8. 데이터 흐름

```text
main.dart
  -> app/app.dart
  -> features의 화면
  -> 해당 화면의 controller
  -> data의 API 또는 로컬 저장 서비스
  -> 앱 모델로 변환
  -> controller 상태 갱신
  -> 화면 다시 그리기
```

화면은 요청 주소, JSON 필드명, `shared_preferences` 키를 직접 알지 않는다. 이러한 세부 사항은 `data` 내부에서만 관리한다.
